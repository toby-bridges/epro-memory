## 先看全局：AI 记忆的三种流派

目前 AI 记忆系统大致分三个方向：

**流派一：云端服务型** — "你把记忆交给我，我帮你管"
> 代表：Mem0、Momo Machine
> 类比：把日记本存在银行保险箱里，安全但不在你手上

**流派二：本地自主型** — "你的记忆你做主"
> 代表：memX、ePro、ClawVault
> 类比：日记本就在你的书桌抽屉里，随时翻阅，不经他人之手

**流派三：学术探索型** — "让我们重新定义记忆该怎么工作"
> 代表：MemGPT/Letta、A-MEM、xMemory、G-Memory
> 类比：记忆研究实验室——理论前沿，但离日常使用还有一段路

我们选了流派二。原因很简单：**个人记忆是隐私数据，不应该离开你的设备。**

### 快速对比表

| 项目 | 谁做的 | 记忆类型 | 存在哪 | 搜索方式 | 去重 | 会遗忘 | 开源 |
|------|--------|---------|--------|---------|------|--------|------|
| **ePro** | 我们 | 智能体工作经验 | 本地 LanceDB | 向量搜索 | 向量预过滤 + LLM 决策 | 暂无（Phase 2） | Apache 2.0 |
| **memX** | 我们 | 用户个人记忆 | 本地 SQLite | 向量 + 关键词 + 图谱 | AUDN 四分类 | Weibull 衰减 | MIT |
| **OpenViking** | 字节跳动 | 通用 Agent 记忆 | VikingDB（字节内部） | 向量 + LLM 重排 | 向量预过滤 + LLM 决策 | 无 | Apache 2.0 |
| **Mem0** | Mem0 AI | 用户/会话/Agent | 云端 Qdrant+PG | 纯向量 | 纯向量相似度 | 无 | Apache 2.0 |
| **MemGPT/Letta** | Letta | Agent 上下文 | Postgres | 纯向量 | 无 | 无 | Apache 2.0 |
| **Graphiti/Zep** | Zep | 时序知识图谱 | Neo4j + 云 | 向量 + BM25 + 图谱 | 图谱边去重 | 无 | Apache 2.0 |
| **ClawVault** | OpenClaw 社区 | Agent 记忆 | Markdown 文件 | BM25 + 向量 | qmd 相似度 | 无 | MIT |

| **ELF** | hack-ink | 证据绑定记忆 | PG + Qdrant | 向量 + BM25 | 向量阈值分级 | 无 | — |

### 每个项目做对了什么？

**Mem0** — 最知名的开源记忆层。做对了一件事：**让"给 AI 加记忆"这件事变得简单**。但它的去重只靠向量相似度（两段话向量接近就判定为重复），容易误判。也没有记忆衰减——记了就永远在，久而久之会堆积大量过时信息。

**MemGPT/Letta** — 开创性地提出"让 AI 像操作系统一样管理自己的记忆"。类比：不是给员工发笔记本，而是让员工自己决定记什么、忘什么。概念超前，但偏重上下文窗口管理，不是真正的长期记忆。

**Graphiti/Zep** — 在时间维度上做得最深：每条信息都带时间戳，能回答"三个月前用户对这件事的看法是什么"。但需要 Neo4j 图数据库 + 云端 LLM，部署成本高。

**A-MEM** — NeurIPS 2025 论文，用"卡片笔记法"（Zettelkasten）组织记忆——每条记忆都有标签、关键词、和其他记忆的链接，形成一张知识网络。理念优雅，但还停留在学术原型阶段。

**OpenViking** — 字节跳动出品，提出了目前最实用的 Agent 记忆分类体系。ePro 的核心架构就来自这里（详见下节）。

**ClawVault** — OpenClaw 社区最成熟的方案。用 Markdown 文件存记忆——你可以直接用文本编辑器打开查看、修改。简单直观，但文件一多搜索就慢了。

## ePro 与 OpenViking：继承与迭代

ePro 的核心设计直接移植自字节跳动的 **OpenViking** 项目。但移植不等于复制——ePro 做了大量工程化改造。

### 从 OpenViking 继承了什么？

**六类记忆分类体系** — OpenViking 定义了 6 种记忆类别（个人信息、偏好、实体、事件、案例、模式），并规定了哪些可以合并、哪些只能追加。这个分类体系经过字节内部验证，ePro 直接采纳。

**L0/L1/L2 三层内容结构** — 每条记忆分为一句话摘要（L0）、结构化概要（L1）、完整内容（L2）。让 AI 先看"书名"，再按需翻"目录"或"全文"。这个设计大幅节省 token（AI 的注意力资源）。

**三套 Prompt 模板** — 从对话中提取记忆、判断新记忆是否重复、合并相似记忆——这三个核心操作的 Prompt 模板直接从 OpenViking 的 YAML 文件移植为 TypeScript 函数。

**两阶段去重流程** — 先用向量搜索找到"看起来相似"的旧记忆，再让 LLM 做最终判断：是新建、合并还是跳过。

### ePro 做了哪些工程迭代？

#### 迭代 1：技术栈现代化

| 方面 | OpenViking | ePro | 为什么改 |
|------|-----------|------|---------|
| 编程语言 | Python | TypeScript | 类型安全，和 OpenClaw（Node.js 生态）无缝集成 |
| 数据库 | VikingDB（字节内部服务） | LanceDB（嵌入式） | VikingDB 不对外开放；LanceDB 零配置，不需要运行额外进程 |
| 配置管理 | Python 字典 + YAML | TypeBox JSON Schema | 运行时自动校验配置，写错参数会立刻报错 |

类比：OpenViking 像一辆性能很好但只在工厂内部使用的定制车。ePro 把发动机（核心算法）拆出来，装到了一辆任何人都能开的标准车上。

#### 迭代 2：安全加固

这是 ePro 投入最多的部分。OpenViking 作为内部项目，运行在受控环境中，不需要太担心恶意输入。ePro 作为开源项目，必须防御各种边界情况。

**防注入攻击** — 如果有人在输入中藏了恶意代码（比如 SQL 注入），ePro 会在入口处拦截。OpenViking 没有这层防护。

类比：内部食堂不需要安检，但开了餐厅就需要。

**LLM 响应解析加固** — AI 模型返回的格式不总是标准的 JSON。ePro 实现了三级解析器：先试标准格式，不行就提取 Markdown 代码块，再不行就用"平衡括号"算法从混合文本中抠出 JSON。OpenViking 只做了基础解析。

类比：翻译一封外文信——OpenViking 假设信永远格式工整，ePro 能处理手写潦草、段落混乱的信。

**并发写入保护** — 多个进程同时写入记忆时，ePro 用写锁串行化防止数据损坏。OpenViking 没有显式的并发控制。

类比：一个笔记本只有一支笔，不会两个人同时在同一页上写字。

**配置范围校验** — 所有数字参数都有合法范围检查。你不能把"最多召回几条记忆"设成 -1 或 999999。

**Prompt 注入防护** — 当记忆内容被注入到 AI 对话时，ePro 会"消毒"其中可能的 XML 标签，防止记忆内容篡改 AI 的行为边界。

**不可变字段保护** — 记忆的 ID、创建时间、来源会话在合并更新时被保护，不会被意外覆盖。

#### 迭代 3：功能扩展

| 功能 | OpenViking | ePro | 说明 |
|------|-----------|------|------|
| 使用频次追踪 | 无 | 有 | 每条记忆被召回时计数，为后续"越用越强"的排序打基础 |
| 分类内向量搜索 | 全库搜索 | 同类别内搜索 | 去重时只在同一类别内找相似记忆，减少误判 |
| L0 精准注入 | 未文档化 | 默认只注入 L0 | 最小化上下文占用，Phase 2 支持高相关度时展开 L1 |
| 共存策略 | 独立系统 | 可与已有插件并行 | 独立的数据库路径和 XML 标签，不和其他记忆插件冲突 |

#### 迭代 4：测试覆盖

OpenViking 仓库中没有公开的测试套件。ePro 有 **106 个单元测试 + 7 个集成测试**，覆盖 7 个测试套件：

| 测试套件 | 测试数 | 覆盖什么 |
|---------|--------|---------|
| 配置校验 | 23 | 参数类型、范围、默认值 |
| 输入验证 | 19 | SQL 注入拒绝、UUID 格式、分类白名单 |
| LLM 解析 | 22 | JSON 提取、Markdown 代码块、平衡括号 |
| 对话处理 | 17 | 消息提取、截断、内容块格式 |
| 记忆提取 | 13 | 提取流程、候选解析 |
| 去重逻辑 | 12 | 向量去重、合并决策、分类感知 |
| 数据库集成 | 7 | LanceDB 读写、向量搜索、并发写入 |

#### 总结：迭代的全貌

```
OpenViking (字节跳动)          ePro (我们的迭代)
─────────────────────          ─────────────────────
Python + VikingDB       →     TypeScript + LanceDB
内部受控环境             →     开源公共环境
基础 JSON 解析           →     三级容错解析器
无并发控制               →     写锁串行化
无输入校验               →     注入防护 + 范围检查 + Prompt 消毒
无公开测试               →     113 个测试 (106 单元 + 7 集成)
~900 LOC 估算           →     1,397 LOC (多出的 55% = 安全 + 测试 + 健壮性)
独立系统                 →     OpenClaw 插件生态共存

核心算法：100% 继承（六分类、L0/L1/L2、去重流程、合并策略）
工程质量：从内部原型 → 生产级开源软件
```

## memX 与 Mem0：两种用户记忆哲学

memX 和 Mem0 都是"用户记忆"项目，但设计哲学截然不同：

| 维度 | memX | Mem0 |
|------|------|------|
| **核心理念** | 你的记忆你做主 | 让记忆管理变简单 |
| **数据存储** | 你的电脑上（SQLite） | 云端（Qdrant + Postgres） |
| **AI 推理** | 全本地 Ollama（零费用） | 云端 API（按量付费） |
| **去重** | AUDN 四分类（新增/更新/删除/忽略） | 纯向量相似度 |
| **会遗忘** | 会（Weibull 衰减 + 三层晋升） | 不会（记了就永远在） |
| **知识图谱** | 有（实体、观察、关系） | 无 |
| **搜索** | 三通道融合（向量 + 关键词 + 图谱） | 纯向量 |
| **费用** | 零（全本地） | 按量付费 |
| **上手难度** | 需要本地安装 Ollama + Node.js | 注册即用 |

**memX 的独特能力：记忆衰减**

这是 memX 和几乎所有竞品最大的区别。大多数记忆系统只管"记住"，不管"遗忘"。时间一长，系统里堆满了过时的信息——你三个月前在做的项目、去年的偏好、早已过期的计划——全部和最新信息混在一起。

memX 用 Weibull 衰减模型模拟人的遗忘曲线：经常被提起的记忆变得更牢固，很久不提的记忆逐渐褪色。这让搜索结果自然地偏向"当前相关"的信息。

类比：一个好的图书馆员不只会买新书上架，还会定期把没人借的旧书移到仓库，确保热门区域永远是最相关的内容。

**AUDN 四分类 vs 纯向量去重**

Mem0 的去重靠向量相似度：两段话的向量足够接近，就判定为重复。但这会漏掉**语义层面的更新**。

例如：你先说"我喜欢 Vue"，后来说"我不再用 Vue 了，改用 React"。纯向量看，这两句话相似度不高（一个讲 Vue，一个讲 React），不会被判定为重复。结果系统里同时存了"喜欢 Vue"和"改用 React"——矛盾的信息。

memX 的 AUDN 管道会让 LLM 做四分类判断：
- **ADD** — 全新信息，直接添加
- **UPDATE** — 和旧记忆相关但有变化，更新旧记忆
- **DELETE** — 推翻了旧记忆，删除旧的
- **NOOP** — 已经知道了，跳过

在上面的例子中，AUDN 会判定为 UPDATE——把"喜欢 Vue"更新为"改用 React"。

## OpenClaw 社区方案对比

除了我们的项目，OpenClaw 社区还有其他记忆方案：

| 维度 | ePro | ClawVault | openclaw-memory | Memory Guardian |
|------|------|-----------|-----------------|-----------------|
| **存储** | LanceDB（嵌入式） | Markdown 文件 | SQLite + Qdrant + PG | Markdown 文件 |
| **搜索** | 向量搜索 | BM25 + 向量 | 三层递进式 | 无搜索 |
| **去重** | 向量 + LLM 决策 | qmd 相似度 | 无 | 无 |
| **分类体系** | 6 类（OpenViking） | 17 类固定 | 无分类 | 无分类 |
| **L0/L1/L2** | 有 | 无 | 无 | 无 |
| **外部依赖** | 无（嵌入式 DB） | 无（纯文件） | Qdrant + PG | 无（纯文件） |
| **核心价值** | 结构化经验积累 | 人类可读可编辑 | 跨 Agent 共享 | 防止 Agent 忘记用记忆 |

每个方案解决的问题不同：

- **ePro** 解决"AI 怎么积累和复用工作经验"
- **ClawVault** 解决"人和 AI 怎么共同维护一份可读的知识库"
- **openclaw-memory** 解决"多个 AI 怎么共享记忆"
- **Memory Guardian** 解决"AI 在忙碌时会忘记查笔记"这个行为问题

## 我们的选择：为什么这样设计

### 为什么做两个项目而不是一个？

用户记忆和工作经验是两种本质不同的信息：

| 特征 | 用户记忆（memX） | 工作经验（ePro） |
|------|-----------------|-----------------|
| 变化速度 | 慢（偏好不常变） | 快（每次任务都可能学到新东西） |
| 隐私敏感度 | 高（个人信息） | 低（工作方法不是隐私） |
| 需要的搜索能力 | 多样（关键词 + 语义 + 关系） | 单一（语义匹配为主） |
| 去重复杂度 | 高（需要理解"更新"和"矛盾"） | 中（主要是"重复"和"合并"） |

硬塞进一个系统，要么对用户记忆不够安全（强制走 API），要么对工作经验过度复杂（不需要知识图谱）。分开做，各自用最合适的技术方案。

### 为什么选本地优先？

我们调研了 Mem0（云端）、Graphiti（需要 Neo4j）、EverMemOS（需要 MongoDB + Milvus + Elasticsearch + Redis 四个服务）。

它们的能力确实强大。但如果你只是想给自己的 AI 助手加上记忆，不想管理一堆云服务或数据库——本地方案是更务实的选择。

memX：一个 SQLite 文件 + 本地 Ollama。
ePro：一个嵌入式 LanceDB。

没有 Docker compose，没有云端账号，没有月费。

### 为什么从 OpenViking 移植而不是从零开始？

因为字节跳动的团队已经在生产环境验证了这套分类和去重体系。六类记忆的划分、L0/L1/L2 的分层、"哪些该合并哪些该追加"的规则——这些设计决策不是拍脑袋想出来的，而是在大量 Agent 对话中打磨出来的。

我们的贡献不在算法创新，而在**工程化**：把一个内部原型变成了可以在开源世界安全运行的生产级软件。这包括安全加固、容错处理、测试覆盖、和 OpenClaw 生态的集成。

### 来自学术界的警告

在调研过程中，我们注意到两个值得警惕的现象：

**Serial Collapse（串行崩溃）** — 来自月之暗面的 Kimi K2.5 论文。AI 可能渐渐"退化"为不使用记忆系统。即使记忆存在，它可能因为查询有延迟成本而越来越少地主动去查。类比：公司买了一套知识库系统，但员工觉得查系统太慢，慢慢就不用了。

**Memory Misevolution（记忆错误进化）** — 来自 TAME 论文。记忆可能积累"有毒的捷径"——看起来高效但其实违反安全约束的经验。类比：一个员工学会了一个"快捷方式"来加速部署，但这个方式跳过了安全检查。

**这两个警告告诉我们：造好记忆系统只是第一步。持续监控记忆质量，是接下来的长期挑战。**
